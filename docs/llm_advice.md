# 診断結果アドバイスのLLM化 進め方メモ

理解負債チェッカー（debt-lens.org）で、診断結果のアドバイスを OpenAI API で生成するための共有メモ。
元資料は「エンジニアリング初学者の学習ファネル（5段階）」の図と、「診断結果のLLM連携 構成と料金比較」（2026-10-25 時点）。

## 1. プロダクトの位置づけ（学習ファネル）

| 段階 | 状態 |
|---|---|
| ① 学習・挑戦 | 教材や課題に取り組む。分からないところを調べながら進める |
| ② 停滞・挫折しかける | エラーや概念で詰まる。AIや記事でなんとなく解決し、理解が追いつかず学習が止まる |
| **③ 原因の特定・次の一手を得る** | **理解負債チェッカーで弱い領域と原因を整理し、今取るべき Next Action を知る** |
| ④ 学び直し・学習への復帰 | Next Action に沿って必要な部分を学び直し、元の学習に戻る |
| ⑤ 学習継続・一人前のエンジニアへ | 自走して学習を続け、ポートフォリオ・就職・実務経験を経て一人前になる |

**プロダクトの支援範囲は ③。** アドバイスの役割は「つまずきの原因」「弱い領域」「具体的な Next Action（学び直しの方向性）」を伝え、④ へ戻すこと。

## 2. 今の診断結果の流れ

1. 質問ページ（クライアントコンポーネント）から Server Action `submitAnswers` を呼ぶ（`front/app/lib/answers.ts`）
2. Next.js のサーバー側で JWT を作り、Rails の `POST /api/v1/results` へ送る
3. `ResultsController#create`（`back/app/controllers/api/v1/results_controller.rb`）で次を処理
   - `Diagnosis::Scoring` でカテゴリ別スコアとAI依存度を計算
   - `CategorySummary` の総評と `choice.feedback` から固定文のアドバイスを作る
   - `results.advices` に保存

**LLM を呼ぶ場所:** `Diagnosis::Advice::GenerateAdvice`（`back/app/models/diagnosis/advice/generate_advice.rb`）を置き換える／拡張するのが一番自然。

### 構成（概要）

```
ブラウザ → Next.js 16 (Amplify, Server Actions + Auth.js)
        → Route53 → ALB → Rails 8.1 API (EC2)
            ├ Diagnosis::Scoring
            ├ Diagnosis::Advice（LLM Client + フォールバック）→ LLM API
            └ RDS PostgreSQL（results / choices / category_summaries）
```

### 処理の流れ

1. ブラウザ → Next.js：回答を送信（Server Action）
2. Next.js → Rails：`POST /api/v1/results`（Bearer JWT, RS256）
3. Rails → RDS：選択肢・カテゴリ・総評を取得
4. Rails：スコア計算（今のロジックのまま）
5. Rails → LLM API：プロンプト（スコア + 回答の要約）
6. 成功ならアドバイス（JSON）を受け取る／タイムアウト・エラーなら今の固定アドバイスで代替
7. Rails → RDS：results を保存
8. Rails → Next.js：`201 {id}`
9. ブラウザ：`/results/:id` に遷移して表示

## 3. 設計のポイント

- **APIキーは Rails 側だけで持つ。** credentials か環境変数に置く。`NEXT_PUBLIC_` 付きの変数に入れるとブラウザに漏れる
- **失敗時は今の仕組みに戻す。** `CategorySummary` と `choice.feedback` の固定アドバイスがあるので、LLM が失敗しても診断は止まらない
- **LLM に送るデータは最小限。** スコアと選択肢の内容だけ。メールアドレスなどの個人情報は送らない
- **LLM の出力は今の `results.advices` と同じ形にそろえる。** フロントと swagger を変えずに済む

## 4. 料金の目安（100回あたり、OpenAI 分のみ抜粋）

試算条件：入力 約3,000トークン／出力 標準 約2,000・悲観 約5,000トークン／100回／総額 $10 以内。トークン数は見積もり（実測ではない）。AWS 費用は含まない。

| モデル | 入力 / 出力（$/1M） | 100回（標準） | 100回（悲観） |
|---|---|---|---|
| gpt-5-nano | $0.05 / $0.40 | 約$0.10 | 約$0.22 |
| gpt-6-luna | $0.10 / $0.50 | 約$0.13 | 約$0.28 |
| gpt-5.4-mini | $0.75 / $4.50 | 約$1.13 | 約$2.48 |
| gpt-6-sol | $2 / $10 | 約$2.60 | 約$5.60 |

- 費用の大半は出力トークン。アドバイスの文字数と出力上限（max tokens）が一番効く
- 思考トークンも出力として課金される
- OpenAI はクレジット前払いなので、入金額がそのまま上限になる
- 単価は 2026年10月時点の値

## 5. 応答時間への対応方針

前提：MAU 100人、月100回程度、同時利用はほぼ1人。開発工数 5日以内。LLM の応答は数秒〜数十秒（未計測）。

経路上のタイムアウト：

| 場所 | 現状 | 備考 |
|---|---|---|
| ブラウザ → Next.js (Amplify) | SSR / Server Action の処理時間の上限 | 公式に明記された値が見つからない。実機で要確認 |
| Next.js → ALB → Rails | ALB アイドルタイムアウト（デフォルト60秒） | 変更可能 |
| Rails (Puma) | スレッド数 3 | MAU 100 なら足りる |
| Rails → LLM API | SDK デフォルトはタイムアウト10分・リトライ2回 | 短く設定し直す必要あり |

共通の打ち手：出力を短くする／軽量モデルを使う／思考を抑える／タイムアウト20〜25秒・リトライ0〜1回を明示する／失敗したら固定アドバイスに戻す

| 手段 | 工数 | 体感 | タイムアウト耐性 | リスク | 5日に収まるか |
|---|---|---|---|---|---|
| **S1. 同期 + タイムアウト + フォールバック** | 2〜2.5日 | △ | △ | 低 | ◎ |
| S2. 同期 + ストリーミング（SSE） | 5日〜 | ◎ | △ | 高 | × |
| A1. Solid Queue ジョブ + ポーリング | 4〜4.5日 | ○ | ◎ | 中 | △ |
| A2. Solid Queue ジョブ + Action Cable | 6日〜 | ◎ | ◎ | 高 | × |

**決定：S1 で始める。** LLM 呼び出しは `Diagnosis::Advice` 内のサービスクラスに切り出し、後で A1 に移る場合もジョブから同じクラスを呼ぶだけで済むようにする。
A1 に切り替える目安：計測した p95 が15秒を超える、または Amplify 側の上限が LLM のタイムアウトより短い。

## 8. 実装手順

1. **今のアドバイスの形を把握する** — `GenerateAdvice` の入出力と、`results.advices` の JSON 構造（キー名・カテゴリ・文字数）を書き出す。これが LLM の出力仕様になる
2. **プロンプトに載せる材料を決める** — カテゴリ別スコア、AI依存度、`CategorySummary` の総評、該当する `choice.feedback`。個人情報は含めない。この組み立て部分は LLM なしでテストできる
3. **プロンプトを手で試す（Rails に入れる前）** — Playground で、スコアが高い人・低い人・偏っている人の2〜3パターンを試す。固定要件（役割、トーン、文字数の上限、弱い領域と Next Action を必ず含める、出力 JSON の形）を決める。Structured Outputs で形を固定する。まず軽量モデルで質を確認する
4. **OpenAI を呼ぶサービスクラスを作る** — `Diagnosis::Advice` 内に切り出す。タイムアウト20〜25秒、リトライ0〜1回、出力トークン上限を明示する
5. **結果を検証し、失敗時は固定アドバイスに戻す** — `GenerateAdvice` を窓口にする。失敗扱い：タイムアウト、APIエラー、JSON が壊れている、カテゴリ欠け、空文字。どちらで生成したかをログに残す
6. **テスト** — LLM クライアントをスタブし、「成功」「タイムアウト」「不正な JSON」の3ケースを確認。本物の API は呼ばない
7. **フロント** — 送信中に「診断中...」を表示し、ボタンを無効化して二重送信を防ぐ
8. **実測して判断する** — 応答時間を5〜10回計測し、Amplify 上で Server Action が何秒まで待てるか確認。p95 が15秒超なら A1 を検討

進める順番：準備 → 1 → 2 → 3（手で試す）→ 4 → 5 → 6 → 7 → 8
